# Registered by ACTIVATION_20261019.md (this note holds on conflict); originally a DRAFT postponed on 2026-10-18 23:1x - Clean rerun of the MICE results on the H800 cluster

An integrity-recovery amendment made after the original results were seen: recomputing the fixed confirmatory and
held-out evaluations with unchanged criteria corrects possible computation faults; it is not new held-out evidence
and not an additional independent sample.

## Why
The local GPU (RTX 5000 Ada, WSL2) corrupted an output silently during Windows nvlddmkm "Graphics FECS Exception"
periods (experiments/gpu_verify_20261018/PLAN.md; Codex gpt-6-astra xhigh: P0, past outputs suspected). FECS events are
recorded in every retained hour with multi-process GPU work since 2026-10-16 05:45, and older periods have no record.
User decision (2026-10-18): every MICE paper result that was computed on the GPU is recomputed on the Tongji cluster
(8 H800); the clean results become the reported version; every original result is kept unchanged.

## What is rerun (tasks.jsonl, generated by make_tasks.py from the original outputs; frozen with this commit)
Every GPU-computed MICE output directory whose computation can be reproduced from committed code (MANIFEST.md),
development runs included, so that no reported number depends on a choice of what to rerun: the run.py family in
MICE/results_* (test, held-out, TabICL backbone, backbone seed 1; development: results_dev, results_grid_dev,
results_dt_dev, results_delay_dev), the probabilities (results_probs), the run roots of rounds 13-14 and the
confirmation sets, the TKDE control run, the pool-capacity, segment-origin and oracle-recall runs, the benchmarks (into
new roots "<root>-h800"), the reconstructed development runs (below), and the Table 1 GPU baselines (Drift-Resilient
TabPFN; dtmoe). 2828 tasks, each with its expected outputs and their structure; recorded original wall time 291 h on
the RTX 5000 Ada (sets with a record), about 400 h in all. Drift-Resilient TabPFN runs only on the cluster: it is not
run on the local GPU (no local output exists; none would be merged).
Development runs are recomputed for the numbers they report; no selection is reopened (the frozen choices below
stay inputs). TOT (Table 1) is registered separately before it runs.
Not rerun, with the reason: CPU-only results (river and trained learners; fsnet / onenet / adaptz / shifts; arf / srp),
which were not exposed to the GPU; results_smoke (not used by the paper).

## Reconstructed runs (user decision 2026-10-18)
Two development runs cited by the paper (main.tex, the TRIM comparison: TRIM = 0 +1.76/+2.09, TRIM = 1 -0.50/-1.24)
cannot be replayed: mice-r14-dev spans three code states of 2026-10-15 11:48-14:44 (between commits 705e7c6 and
e62ebce), and mice-r14-devtrim ran TRIM = 1 from uncommitted code minutes before commit 991a1f9 introduced
CPSegments.TRIM. Both are recomputed on the registered commit: mice-r14-dev with experiments/mice_r14/run_task.py as it
is, mice-r14-devtrim with run_task_trim1.py (the same run_task.py with the class attribute CPSegments.TRIM = 1). They
are reconstructions, not replays: the paper labels them so, and their old-new differences are reported but not read as
evidence of a computation fault. Their tasks without an original output (16 d_bvarr tasks of mice-r14-dev that never
finished) are not added. Derived replays ("mice", "mice2", ...) and every
CPU analysis that reads GPU outputs are recomputed from the new outputs by the existing scripts.

## What stays the same
- Code: the repository at the commit that registers this plan. The computation code of every rerun method is that of
  the original runs: MICE/code/run.py changed since 2026-10-05 only by additions (new methods; 7 deleted lines extend
  method lists), the TKDE control run uses its own code snapshot (source/, controller/: run.py = commit 7525ac8), the
  round-14 and later runs used the current run.py (unchanged since 2026-10-15 15:14).
- Data, task lists, seeds, B, constants, environment variables of each original run (OMP_NUM_THREADS = 4 for the
  run_scripts of MICE/results_*, 1 for the later roots), and the original commands (tasks.jsonl).
- Frozen choices are inputs, never recomputed: the frozen MICE configuration, the regime / detector constants, k* of
  kstar.json, M* of m_star.json, the development selections of every registered round. The registered criteria and
  hypotheses are evaluated on the new results by the same analysis code, unchanged.
- Python environments: the package versions of env_lock/ (venv: torch 2.14.0+cu126, tabpfn 9.0.0, tabicl 2.2.0;
  drtabpfn: torch 2.1.2+cu121; totgpu: torch 2.3.1+cu121). All three include kernels for sm_90 (H800).

## What changes
- Hardware: H800 (Hopper), native Linux, Slurm; every rerun on the same GPU model. Results are not expected to be bit
  identical to the originals (different GPU, kernels, float order); differences are reported, not corrected.
- Concurrency: several processes per GPU (each task in its own process), as many as run without failure.
- dtmoe (Table 1 baseline, not a frozen MICE result): strict deterministic mode (gpu_verify AMENDMENT_20261018b), its
  whole development grid (180 tasks) and then its test runs on the H800; the local dtmoe results are not used.

## Identity of inputs (checked on the cluster before the probe)
Data, task lists, code snapshots and frozen selection files are bundled from the original locations with per-file
SHA-256 (bundle SHA256SUMS), checked on the cluster. Code: the registered commit; the TKDE control run uses its bundled
snapshot. Model weights: TabPFN v2 checkpoint from the original cache (bundled, hash recorded); TabICL: the default
checkpoint of the same tabicl version (2.2.0, tabicl-classifier-v2-20260212.ckpt; the package versions of the venv
are those committed on 2026-10-06, after the first TabICL runs of 2026-10-04/05) - downloaded, hash recorded; this is
the one input whose identity with the original cannot be checked byte for byte (the original file is not kept).
Any other difference found is recorded and stops the affected set until the coordinator registers its disposition.

## Checks before and during the runs (rerun.py, HANDOFF.md)
1. Determinism probe on the H800, before production: the tasks listed in HANDOFF.md (one per pipeline; dtmoe L16 and
   two L32 configurations) run twice in fresh processes; every saved array (wall time and peak memory excepted) and
   every other output file must be byte-identical. A pipeline that fails pauses: its evidence is kept, the cause is
   diagnosed, and its disposition is registered (coordinator, arbiter, user) before any of its production runs;
   dtmoe keeps its registered fallback (gpu_verify AMENDMENT_20261018b). Passing does not certify every task or GPU.
2. During production: GPU health (ECC errors, throttling) is recorded before and after every attempt; once per set,
   one finished task is replayed under production concurrency into a probe directory and must be byte-identical to
   its production output (same disposition rule on failure).
3. Failures: every attempt starts from initialisation; partial outputs and checkpoints of a failed attempt are moved
   to a quarantine directory, never resumed; at most 3 attempts (benchmarks 1). A task is accepted only with return
   code 0 and every expected output present and loadable - an acceptance rule that never looks at a score.
4. Completeness: every task done (rerun.py status); counts equal those of the originals.
5. Provenance: per task the host, GPU name, driver, start, end, attempts, return codes, health records.

## Benchmarks and frozen selections
The benchmarks are measurements only on the H800: they write into "<root>-h800"; k* (kstar.json) and M* (m_star.json)
of the original roots stay the frozen inputs of the runs that use them and are never recomputed or replaced. The
analysis of the H800 benchmarks (budget compliance of k* and M* on the H800, timing tables) needs path adaptations of
analyse_pools.py / analyse_14b.py / analyse_bench.py that separate measurement from selection; they are registered
and audited before that analysis. Claims of cost matching are re-evaluated on the H800 numbers, not carried over.

## Reporting rule
The paper reports the H800 results. An appendix section states the incident, the hardware of the reported results and
the differences to the original results: per table and figure, the change of each reported number; per number in the
text; per registered criterion, the decision on the original and on the new results, with uncertainties where the
paper gives them; and the results not rerun with their reason. A registered conclusion that changes is reported as it
is on the new results, in the abstract and main claims as well; exploratory and confirmatory labels are kept; the
user decides the wording. Old-new differences alone are not read as evidence of corruption. The original results and
their analyses stay in the repository and in ~/pfn-runs, unchanged.
