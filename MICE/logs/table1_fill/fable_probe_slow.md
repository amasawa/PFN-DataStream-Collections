**决定：B 的变体 —— 先取一次栈快照作证据，然后立即停止探针，启动 DR；dtmoe 的去留在 DR 期间提交用户裁决。**

**Decision**
- 停止当前探针（保留全部产物与日志，移到 `dtmoe_local/probe_pre/aborted_<ts>`，不删除），立刻启动 DR 链。
- 停止前先做一次无侵入栈快照（`py-spy dump --pid <pid>`，若未安装则 `cat /proc/<pid>/stack` + `nvidia-smi` 截图），记录是哪个算子在热路径上。这是回答"为何慢"的唯一廉价证据，等探针跑完并不能给出这个信息。
- 探针顺序改为 DR 之后（3a 与 3b 互换）。这是调度变更，不是方法变更：探针与 DR 相互独立，amendment d 第 4 条已写明"dtmoe 失败时 DR 照常进行"。

**Supporting evidence**
- 已知下界已足够做决定：≥40x 意味着 180 任务网格 ≥150 GPU 小时，加上扩展与书挡探针，远超本地 GPU 预算，无论精确倍数是 40x 还是 80x，结论相同。等它跑完（C）只能把下界变成点估计，代价未知（可能再 1–3 小时），不改变任何行动。
- DR（~83 h）是关键路径，每推迟 1 小时就是实打实的 1 小时。
- 36% GPU 利用率 + 82% 单进程 CPU 与"确定性 scatter/index 回退被串行化、大量小 kernel 启动"的画像一致，与驱动事件或挂死不一致（无错误、进程仍活跃）。

**Alternative options**
- C 加硬上限（例如到 01:15 为止，不到即停）：多花 ≤40 min 换一个精确倍数。仅当用户明确需要精确数字做 H800 预算估计时才值得。
- A：按登记执行。不建议，≥6 h 延迟换来的信息对 DR 无用，而且探针即使通过，网格也不可行，还是要回到用户裁决。

**Key risks**
- 误归因：如果 21:0x 的非确定性运行时 12 条 CPU 扩展通道也在跑，则 CPU 争用已被控制变量排除；若不是，当前慢的一部分可能来自争用，栈快照和记录"扩展通道占用情况"可以保住这个判断。
- 停进程后 GPU 显存残留：杀进程后用 `nvidia-smi` 确认 1.6 GB 已释放，再启动 DR 的首个 canary。
- 书挡设计假设 probe_pre 在网格之前：顺序互换后仍成立（probe_pre 仍在网格前），不影响第 7 条。

**What to record（写入 run log + AMENDMENT e 或 d 的 deviation 段）**
- 时间戳、pid、已运行时长、GPU util/mem、CPU%、栈快照原文、两次非确定性参照时长（71–75 s，12:48 与 21:0x）及当时 CPU 通道状态。
- 决定、顺序变更理由（调度而非方法）、探针产物归档路径、DR 启动时间、fecs_watch 连续性未中断。
- 明确写明：dtmoe 路径状态为"strict 模式可行性未决，待用户裁决"，不是"失败"也不是"通过"。

**Remaining uncertainty**
- 精确倍数未知（只有 ≥40x 下界）。
- 是否存在中间方案（仅对 MoE 路由算子放宽确定性、或在 H800 上 strict 模式是否同样慢）属于协议变更，需用户决定，不在本问题范围内。

**Confidence**：约 0.8 支持 B 变体；0.15 支持 C 加上限；A 基本排除。

**Requires user approval**
- 顺序互换与停止探针：不需要，作为 deviation 记录即可（符合"只在方法变更或新数据时停下问用户"的既定规则）。
- dtmoe 的最终处置（放宽确定性、改到 H800、或从 Table 1 中撤下）：需要用户，按 amendment b/d 第 4 条。DR 运行期间提交给用户即可，不阻塞 DR。
